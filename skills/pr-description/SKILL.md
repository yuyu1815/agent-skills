# pr-description — 10 秒で分かる PR 本文

## 前提

「コードがドキュメントなら、PR の文章は人が知るべき最短経路」。
読み手はまず図を見て全体を掴み、必要な人だけ下へ読み進める。上ほどやさしく、下ほど細かくする。

## 構成（この順）

### 1. PR チェーン（stacked PR のときだけ、最上部）

今どこにいるかを一目で分かるようにする。現在の PR を太字にする。
以下の番号・名前・パスは架空の例。実際の内容に合わせて書く。

```markdown
#101 データ準備 ✅merged → **#102 保存処理（この PR）** → #103 表示 ⏳
```

チェーンが長い・分岐するなら mermaid の flowchart LR にして、現在の PR のノードに色を付ける。
マージ順の制約があれば 1 行添える（「#101 のマージ後にマージする」）。

### 2. issue

`issue: <URL>` を 1 行。

### 3. 図（最初の 10 秒）

PR の抽象度に合う mermaid の図を選ぶ。flowchart に決め打ちしない。
掲載先で対応する図の種類と記法を使う。未対応の場合は、伝えたい関係を保って文章や表に組み直す。

| 変更が主に変えるもの | 図 |
|---|---|
| システム・コンポーネント間のやりとりの順序 | `sequenceDiagram` |
| 状態と遷移（ステータス、審査、移行） | `stateDiagram-v2` |
| クラス・モデルの関係、責務の移動 | `classDiagram` |
| データの持ち方（テーブル・関連） | `erDiagram` |
| サービスやインフラの配置 | `architecture-beta`（掲載先が対応している場合） |
| 分岐の多い判定ロジック | `flowchart` |

- 変更前と変更後を**同じ図の種類・同じ登場要素**で並べ、違いだけが目に入るようにする
- 変わった箇所に「今回追加」「今回変更」と印を付ける
- 登場要素はクラス名でなく役割名で書く（「データ取得処理」「保存 API」）
- 図が 1 枚で足りるなら 1 枚でよい。図にする価値がない小さな PR では省いてよい

### 4. 要約と挙動の変化

- 要約は 2〜3 文。何が困っていたか → 何をしたか → 判断したこと（「未入力でも処理は止めない」）
- 挙動の変化は表にする。行が状況、列が変更前 / 変更後。正常系だけでなく、失敗・空値・既に処理済みなどの端のケースも入れる
- 変えていない振る舞いは「変更なし」と明記する
- ここまではプロジェクト内部の名前を前提にせず、読み手に通じる役割や動作の言葉で書く

### 5. 変更点（レビュアー向け）

ファイル名・クラス名を使ってよい。1 ファイル（またはまとまり）1 行で、何をなぜ変えたか。

### 6. 確認（TODO 形式）

文章で経緯を書かず、チェックリストにする。確かめたものは `[x]`、未確認は `[ ]` のまま残す。

```markdown
- [x] 検証環境でデータを取り込み、必要な項目が保存されることを確認
- [ ] 外部 API の取得失敗時の挙動（検証環境で再現できず未確認）
```

関連するテストがあれば、レビュアーがそのまま貼れるコマンドを載せる。
実際のプロジェクトで有効なコマンドを使う。以下は Ruby / RSpec の架空例。

```bash
bundle exec rspec spec/models/data_importer_spec.rb spec/requests/data_imports_spec.rb
```

## 注意

- リポジトリに PR テンプレート（`.github/PULL_REQUEST_TEMPLATE.md` 等）があれば、その見出しは残し、中身をこの構成で埋める
- 公開リポジトリ（`gh repo view --json visibility` で確認）では、非公開の組織名・システム名・リポジトリへの参照・内部リンクを書かない
- クレジットの記載は、利用するエージェントの指示とプロジェクトの方針に従う
